section: Changed
---
Make compliant goes over MQTT first like every other change: for a device that is online on TasmoFleet's broker with its own topic, the settings are sent over MQTT in the same chunks as before, followed by the one save. A chunk with a change of the device's MQTT connection (its topic, broker or login) still goes over HTTP while HTTP works; when HTTP does not work such a line is left out and listed as skipped, as before. A chunk MQTT sent and the device did not confirm is reported as an unknown outcome and never sent again. The audit's "via" now says "mqtt" for these runs. A policy rule that names a setting with a number it does not take (Topic1, MqttHost0) is now refused with "write the setting as Topic", and a stored one is left out with that reason: Tasmota drops the number and sets the setting, but TasmoFleet did not know that the line restarts the device or changes its MQTT connection, and did not check its value. The same goes for a SetOption under another name: a rule with a SetOption synonym (MqttTLS, MqttNoRetain, DiscoverOff, ChannelRemap, ...) is refused with "write the setting as SetOption103", and a SetOption number or value with a leading 0 is refused: Tasmota reads SetOption003 as SetOption3 (refused with "write the setting as SetOption3") and a value such as 08 as octal (refused with "write the value as a plain decimal") (#606)
