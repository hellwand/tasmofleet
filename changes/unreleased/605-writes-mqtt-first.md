section: Changed
---
Changes go over MQTT first, like reads since 0.30.0: console and settings writes, Restart, bulk commands and the switches of a device that is online on TasmoFleet's broker with its own topic (its group topic read, and every other device's) are sent over MQTT, and over HTTP only when nothing could be published. A change MQTT sent and the device did not confirm is reported as an unknown outcome and never sent again. A change of the device's MQTT connection (topic, broker, login), a password or Wi-Fi name, the range extender's included, a BLE sensor bind key (MI32Key, MI32Keys) or the Zigbee network settings (ZbConfig), or a login inside a command such as an OtaUrl with user:pass@ (they would cross the broker in clear text) and a GPIO template still go over HTTP while HTTP works, and Make compliant keeps HTTP first for now. Console and bulk commands whose arguments the audit hides (it logs them as "Name ***") keep HTTP first while HTTP works too, whatever the command: a secret can hide in any command typed there. Over MQTT, If, DevGroupSend and LoRaCommand are now refused like the other commands that run commands (they go over HTTP), and a device reply no longer shows the Zigbee network key (KeyL, KeyH) or the BLE bind keys (MIKeys). The audit names the transport, and the device page's "How TasmoFleet reaches this device" card says which way changes go and why; the console's title names the transports ("MQTT + HTTP", "MQTT" or "HTTP") instead of always "HTTP". The console and bulk commands now ask for a confirmation before they set RgxPassword or RgxSSId (the range extender's Wi-Fi password and name) or WiFiTest (a Wi-Fi name and password to try), as for the other passwords and Wi-Fi names, and before MI32Key, MI32Keys or ZbConfig with a value, naming what a wrong key or a changed Zigbee network does (#605)
